Experiment 2 of 4 · robot benchmark

Does a trust map keep the robot safe?

A geometry score only matters if it changes what a robot does. So we let a simulated robot plan inside a generated world, then make it drive the same path in the true world and count collisions.

What you will learn

Whether a trust map changes what a simulated robot does when it plans inside a generated world.

Key takeaway

Inconclusive: the benchmark was underpowered, and no trust policy beat the standard "unknown = obstacle" rule.

The setup

What the robot does

A 2D disc robot starts at the prompt camera. It plans on a floor-plane map built only from the generated splats, then executes the path in the truth map. A collision is touching a truth obstacle; a fall is entering a truth cell with no floor. 40 goals per case across 12 cases (480 goals): up to 20 in regions the photo saw, where any exist (95 of 480 goals, in 5 of 12 cases), and the rest in regions it did not.

The policies compared

No mask: trust everything generated. Frustum, visibility, ours: treat low-confidence regions as unsafe. Unknown = obstacle: the standard conservative occupancy-mapping rule, and the baseline that matters. Oracle: plans on the true map, as a sanity check.

Read this firstIn the first run three of the policies show 0% of goals reached. That is a flaw in the test design (the robot's own blind zone traps every cautious policy), not evidence about trust maps. The explanation is below the charts.

Compared with "unknown = obstacle"

The success criterion pre-specified before the run: a trust policy must match the baseline's safety (failure-rate difference with a small upper bound) and be better on completion or path length. Each point is a mean paired difference over 12 cases with a 95% bootstrap interval.

Why the answer is inconclusive, not negative

As originally specified, the three trust policies completed nothing.That is a design artifact, not a finding about trust. Two causes: the floor-height estimator locked onto a wall or tabletop slab (floor height off by 0.15 scene units or more) in 8 of 12 cases, and the camera looks level so the floor within about 1.6–2 units of the start sits below the frustum, which traps every conservative policy at the start cell.
The amended run was changed after seeing the outcomeFour amendments (true floor height, free blind zone, free robot footprint, camera-based alignment) were made after run 1 and are logged in prereg/RQ1.md. The free blind zone was added only to the trust policies' maps, but a post-hoc check (results/WP1-sensitivity.md) found that the baseline's own map already treated those cells as free in all 12 cases, so it did not tilt the comparison. The amended maps do use the true floor height. That run cannot confirm the hypothesis; it only suggests that once the artifacts are removed, trust policies are indistinguishable from "unknown = obstacle", and unmasked planning is less safe.

What a better benchmark needs

A real floor estimate

Use the exported ground-plane offset, or fit the floor robustly, instead of the most common height.

A camera that sees the floor

Pitch the prompt camera down, or start the robot where the floor is in frame.

More power

Many more worlds and goals; "unknown = obstacle" completed anything in only a few cases here.

Circularity audit
  • The generated world's filled-in region is our own room-box prior, so "unseen means obstacle or hole" is partly built in.
  • The truth world is a public example splat world whose exported surfaces can be less complete in areas the camera did not cover, and the robot can fail there regardless of the generator.
  • Oracle completed 100% of goals with 0 failures in all 12 cases, so the executor and truth map behave as intended.
