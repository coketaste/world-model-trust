Experiment 2 of 4 · robot benchmark

Does a trust map keep the robot safe?

A geometry score only matters if it changes what a robot does. So a simulated robot plans inside the generated world, then drives that path in the true world while we count collisions.

What you will learn

Whether a trust map changes what a simulated robot does when it plans inside a generated world.

Key takeaway

Inconclusive: the benchmark was underpowered, and no trust policy beat the standard "unknown = obstacle" rule.

The setup

Goals

40 goals per case, 12 cases (480 goals). Up to 20 per case lie in regions the photo saw (95 goals, 5 cases); the rest lie in regions it did not.

The policies compared

No mask trusts everything. Frustum, visibility and ours treat low-confidence regions as unsafe. Unknown = obstacle is the standard conservative rule and the baseline that matters. Oracle plans on the true map.

Read this firstIn the first run three policies reach 0% of goals. That is a flaw in the test design (the robot's blind zone traps every cautious policy), not evidence about trust maps. Explained below the charts.

Compared with "unknown = obstacle"

The success criterion pre-specified before the run: a trust policy must match the baseline's safety (failure-rate difference with a small upper bound) and be better on completion or path length. Each point is a mean paired difference over 12 cases with a 95% bootstrap interval.

Why the answer is inconclusive, not negative

As originally specified, the three trust policies completed nothing.A design artifact, not a finding. The floor height was wrong in 8 of 12 cases, and a level camera cannot see the floor within about 1.6–2 units of the start, which traps every conservative policy there.
The amended run was changed after seeing the outcomeIt cannot confirm the hypothesis. It only suggests that, with the artifacts removed, trust policies are indistinguishable from "unknown = obstacle", and unmasked planning is less safe.
The four amendments and the sensitivity check
  • Amendments after run 1: true floor height, free blind zone, free robot footprint, camera-based alignment. All are logged in prereg/RQ1.md.
  • The free blind zone was added only to the trust policies' maps. A post-hoc check (results/WP1-sensitivity.md) found the baseline's own map already treated those cells as free in all 12 cases, so it did not tilt the comparison.

What a better benchmark needs

A real floor estimate

Use the exported ground-plane offset, or fit the floor robustly, instead of the most common height.

A camera that sees the floor

Pitch the prompt camera down, or start the robot where the floor is in frame.

More power

Many more worlds and goals; "unknown = obstacle" completed anything in only a few cases here.

Circularity audit
  • The generated world's filled-in region is our own room-box prior, so "unseen means obstacle or hole" is partly built in.
  • The truth world is a public example splat world whose exported surfaces can be less complete in areas the camera did not cover, and the robot can fail there regardless of the generator.
  • Oracle completed 100% of goals with 0 failures in all 12 cases, so the executor and truth map behave as intended.
